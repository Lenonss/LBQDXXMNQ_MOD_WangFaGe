## 0. 摘要：先给结论

1. **字段层面 0 条硬违规。** 我们 4 个文件出现过的每一个元素名、每一个枚举字面量、每一个被引用的 Name，在原版里都有先例或存在于引擎类型定义中。`docs/调研-引擎失败点.md`（另一路调研）独立得出同一结论。
2. **原版 24/24 必有的 Gong 子元素只有 6 个**：`DisplayName`、`Desc`、`SelectDesc`、`FiveBaseNeed`、`ElementKind`、`Stages`。我们 6 个全有。
3. **`<SkillSetName></SkillSetName>` 是空值，这完全不是问题**：原版 17 个写了该元素的功法**全部是空标签，非空 0 个**，另有 7 个干脆不写。C# 侧对 `Gong.SkillSetName` 的消费点为 **0 处**（只有 XLua/ObjectTranslator 暴露给 Lua）。这一项可以从怀疑清单里划掉。
4. **参悟树 `Level`/`Index` 全部合法**：我们 9 个节点落在 `Qi/Dan1/Dan2/God` 四行、`Index` 0–3；原版 578 个节点覆盖 `None/Qi/Dan1/Dan2/God/God2` 六行、`Index` 0–11。行取 `Level-1`、格取 `Index` 的写法（`Wnd_GongSkillTree.cs:90-91`）在我们这里不会越界。
5. **Stage 数值全部落在原版区间内**：`Value` 1800–70000（原版 1–50,000,000）；`Chance.CostTime` 50–900（原版 1–1200）；`God.ThunderValue` 520000（原版 420000–1250000）；`God.NeckCountdown` 3000（原版 3000–18000）；`Thunder.ThunderValue` 10000（原版 8000–100000）；`Thunder.NeckCountdown` 4900（原版 1800–4900）；`Explore.ExploreValue` 1.0/1.2（原版 1–12）。
6. **真正"原版从不这么写"的有 4 处**：树节点的 `<DaoHang>`（原版 578 个节点 **0 次**）、显式 `<Depth>0</Depth>`（原版只写 `<Depth>1</Depth>`，34 个）、`ElementKind=Mu` 配全 `-1` 的 `FiveBaseNeed`（原版 0 例）、秘籍 `Type=Skill` 却挂 `<Magics>`（原版 `Type=Skill` 的 36 本 **0 本**带 Magics；但第三方 9 本里 6 本这么写）。
7. **唯一实质性越界在 Modifier 的数值语义**：引擎公式是 `((base*(1+basep)+basev)*(1+addp))+addv`（`PropertyMgr.cs:395` / `BodyPractice.cs:166`），即 **`AddP`/`BAddP` 是"比例"不是"百分数"**（0.5 = +50%）。我们把 `BAddP=200`、`BAddP=300`、`AddP=10/30/50/100` 当百分数写 → 实际是 **×201、×301、×11、×31、×51、×101**。原版同一属性上 `NpcLingMaxValue` 的 `BAddP` 上界是 **1**，我们超了 **200 倍**。
8. **结论**：这套配置**不足以解释"引擎 UI 崩坏"**——它能解释的是"数值爆表/面板数字离谱"。会静默炸 UI 的是另外几个引擎缺陷（`CurStage` 为 null、`Necks` 为 null、`(stages.Count-1)` 除零），见 `docs/调研-引擎失败点.md`，本报告不重复。

### 2.3 `FiveBaseNeed` 格式（唯一有解析器的字段）

`GongDef.GetFiveBaseNeed()`：

```csharp
string[] array = FiveBaseNeed.Split(',');
for (int i = 0; i < array.Length; i++) FiveBase[i] = int.Parse(array[i]);
```

- 必须是**逗号分隔的整数**，个数 **≤5**（`FiveBase` 长度 5；循环上界是 `array.Length` 而不是 5，写 6 个整数会 `IndexOutOfRange`）。
- 原版 24 个值里 11 个是 `-1,-1,-1,-1,-1`（**全部 ElementKind=None 的功法**），其余 13 个各不同，格式**带空格**（如 `-1, 7, 5, 6, -1`、`8,-1,-1,5,3`）。
- 我们（`Settings/Practice/Gong/Gong_YanTian.xml`，**267 行，16:56 被改过**）：`L6 <FiveBaseNeed>-1, -1, -1, -1, -1</FiveBaseNeed>` → 5 个整数、带空格，**格式合法**。
- **但组合无先例**：原版 11 个全 `-1` 的功法**全部** `ElementKind=None`；原版两门 `Mu` 功法是 `8,-1,-1,5,3`（`Gong_2_Mu`）和 `4, 6, -1, 6, 3`（`Gong_9_Mu`）。我们现在是 **`ElementKind=Mu` + 全 -1** —— `Mu` 配全 -1 的原版先例 **0 个**（13 个五行功法的 `FiveBaseNeed` 都含正整数）。
- 后果：`GameDefine.GetElementColor(Mu)` 返回木色（不再是 `None` 的黑），世界模型灵体材质会变绿；五行需求全 -1 意味着**不要求任何五行资质**即可修 → 玩法放宽，不崩。

## 4. `SkillSetName`（重点结论：不是问题）

| 口径 | 数字 |
|---|---|
| 原版写了 `<SkillSetName>` 的功法 | **17 / 24** |
| 其中**非空**的 | **0** |
| 其中空字符串的 | **17** |
| 完全没写该元素的 | 7 |
| 第三方（3 个功法） | 2 个写空标签，1 个不写 |
| 官方 Example | 1 个写空标签 |
| **我们** | 1 个写空标签（`Gong_YanTian.xml:7`） |

原文片段（我们）：

```xml
<SkillSetName></SkillSetName>
```

空字符串 vs 不写元素，两者在 `GongDef` 里都是 `null` 或 `""`，而**没有任何 C# 代码读取 `Gong.SkillSetName`**（全文搜索反编译源，命中的只有 `XLua/ObjectTranslator.cs` 的通用字段导出，不是业务消费点）。它是个历史遗留字段。

**判定：`<SkillSetName></SkillSetName>` 与原版主流写法逐字节同构，删除或保留都不影响任何 UI。这一条可以从"可疑"清单里彻底划掉。**

`SkillSetName` 与 `<Skill>` 列表也没有对应关系：原版 17 个空 `SkillSetName` 的功法里，8 个 `Skill` 为空、9 个有 1–3 个 `li`，空值不影响 `Skill` 生效。

### 6.4 关键：`AddV` / `AddP` / `BAddV` / `BAddP` 的语义（这是本次唯一实质性发现）

引擎统一公式（`XiaWorld/PropertyMgr.cs:395`，`_GetNormalProperty` 同款；`BodyPractice.cs:166` 与 `Wnd_BodyPractice.cs:303` 出现同一式子）：

```csharp
return Mathf.Clamp(
    ((num * num2 + def.AddValue) * (1f + basep) + basev) * (1f + addp) + addv,
    def.MinValue, def.MaxValue);
```

即：

```
最终值 = ((基础值 × (1 + BAddP) + BAddV) × (1 + AddP)) + AddV
```

- **`AddV`、`BAddV` = 绝对值**（+0.15 就是 +0.15）
- **`AddP`、`BAddP` = 比例（不是百分数！）**：`0.5` = +50%，`1` = +100%（翻倍），`10` = **+1000%（×11）**，`200` = **×201**，`300` = **×301**

原版数据的用量分布（`AddV` 1566 / `AddP` 1221 / `BAddP` 170 / `BAddV` 49）证明 `BAddP` 是"小比例"：原版 `NpcLingMaxValue` 的 `BAddP` 取值只有 `0.002`、`0.02`、`0.1`、`0.2`、`0.25`、`0.3`、`0.5`、`1`、`-0.01`、`-0.1`、`-0.9` —— **上界 1**。

**我们把 `BAddP=200`、`BAddP=300` 当"百分数"写，实际是 ×201 / ×301。** 详细越界清单见 7.3。
