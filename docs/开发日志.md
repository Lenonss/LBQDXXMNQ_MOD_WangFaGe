## 2026-11-14 · 参悟树空白修复 + 境界显示说明

### 问题一：功法参悟树全空（已修）
反编译 `Wnd_GongSkillTree.UpdateDate()` 得到填充逻辑：
```
var row = UIInfo.m_tree.GetChildAt((int)def.Level - 1);
var btn = row.m_n144.GetChildAt(def.Index);
```
`def.Index` 是**该境界行内**的格子下标，不是全树序号。先前 11 个节点用了全局 0..10，
Dan1/Dan2/God 行 `GetChildAt` 越界返回 null，随后 `.visible = true` 抛 NRE，
循环中断 → 所有节点已被隐藏 → 整棵树空白。

修正：`Settings/Practice/Tree/Gong_YanTian.xml` 改为分境界从 0 起编号
（Qi 0/1/2、Dan1 0/1、Dan2 0/1/2/3、God 0/1）。官方实测各境界行 Index 上限 Qi~God 均为 11，God2 为 8。

### 问题二：末段显示「元神期」而非「在世仙人」（引擎机制，非 bug）
- `GameDefine.GetGongStageLevel(level)`：`>=10 → God(元神)`，`>=7 → Dan2`，`>=4 → Dan1`，否则 `Qi`。
  功法阶段的境界标签完全由 Stage@Level 推导，Level 12 必然显示「元神期」。
- `NpcPractice.GongStateLevel`：`if (GodCount > 0) return God2(在世仙人);` 否则用上式。
  即「在世仙人」= **渡过天劫**（`AddGodCount(1)`），是角色状态，不是某个阶段 Level 能直接标注的。
- 因此：九境最后一关「天门·飞升」渡劫成功后，角色自动进入「在世仙人」；渡劫前的阶段标签显示元神期是正确表现。

### 问题三（真因）：秘籍 `StarLevel` 越界触发 UI 控制器异常（已修）
上面两条都不是根因。用游戏内置控制台（Debug mod 的 `Wnd_ConsoleWindow`，`DO` 执行 `LuaMgr.Instance.DoString`）实测：

- `CS.Wnd_GongSkillTree.ShowSkillTree("Gong_1_Shui")`（官方功法）→ 正常渲染。
- `CS.Wnd_GongSkillTree.ShowSkillTree("WFG_Gong_YanTian")` → 立刻空白，控制台打出红字：
  `LuaException: at FairyGUI.Controller.set_selectedIndex ... at Wnd_GongSkillTree.UpdateDate()`
- 运行时读取格子控制器页数：`m_Mode.pageCount=2`、`m_Level.pageCount=3`、`m_State.pageCount=3`。
- `Wnd_GongSkillTree.cs` 第 137 行：`m_Level.selectedIndex = esotericaTemplate.StarLevel;` —— **StarLevel 直接作为控制器索引**，
  合法范围只有 0..2。官方 474 本秘籍的 `StarLevel` 实测只有 0/1/2（213 个 1、180 个 2、81 个 0）。
- 本项目 `Esoterica_YanTian.xml` 写了 3 和 4 → 参悟树填充循环处理**第一个节点**（Qi 行 A0，挂 `WFG_Eso_YanTian_Gong`，StarLevel=3）时即抛异常，
  循环中断 → 5 行 × 12 格全部停留在「已隐藏」状态 → 整棵树空白。这也解释了为什么数据探针全部正常却看不见。

修正：
- `Settings/Esoterica/Esoterica_YanTian.xml`：9 本秘籍 `StarLevel` 全部压到 0–2（原 3/4 改 2）。
- 恢复完整 11 节点参悟树（Index 分境界从 0 起，每节点均挂 `Esoterica`）。
- 结论固化：**mod 秘籍的 `StarLevel` 必须落在 0..2，否则功法参悟面板会整体空白且只在控制台留下 Controller 异常**。

### 顺带修掉的两处运行时隐患
- `Scripts/WFG/stage.lua` `S:List()`：`World.map.Things:GetPlayerActiveNpcs()` 返回 **C# `List<Npc>`**，
  直接 `#list` 会报 `attempt to get length of a System.Collections.Generic.List`1[...]`，
  1 秒心跳每 tick 抛错 → 自愈/境界派发全部失效。已改为按 `.Count` + 0 基下标拷进 Lua 表。

## M5 · 收尾完善（2026-11-14 15:2x）

### 一、修掉一个致命缺陷：造物 API 不存在
`ThingMgr:CreateItem` 在整个 DLL 里**没有实现**（只有 `CreateItemThingByRewardInfo`）。此前的 `WFG.item:Create` 用 `pcall` 包着调用，失败被静默吞掉 —— 也就是说 **M3 的「创造」和 M4 的「炼制法宝」100% 不会产出任何东西**，只是提示成功。

改用引擎原生落格接口：
```lua
World.map:DropItems(defName, nil, count, key, true, true, 0, addq)
```
- 第 4 参 `key` 是落格坐标，传角色 `npc.Key`；第 8 参 `addq` 是品级增量（float 0..1），品级 1~5 映射为 `(q-1)*0.2 + 0.1`。
- 三级回退：`DropItems` → `AddItemThing` + `Map:DropItem` → 旧 `CreateItem`；全失败才写日志。

## 2026-11-17 · 解析流程修错与确认弹窗

### 现象（用户实测）
1. 施放「衍天·解析」后弹窗「灵气不足：需要 50，当前 0」。
2. 灵气明明超过 50，仍提示不足。
3. 希望施放前先弹可操作确认窗：显示物品与消耗；灵气不足时只留关闭，足够时才出现「开始解析」。

### 根因
- 本作 NPC 的**当前灵气属性名是 `LingV`**（`XiaWorld/Thing.cs:413 public float LingV { get; protected set; }`），根本不存在 `Ling`。
- `Scripts/WFG/core.lua` 的 `WFG:Prop` 对不存在的键返回默认值 0，于是所有 `Prop(npc,"Ling")` 恒为 0：解析判定、创造判定、自愈回灵、总库存取全部按「灵气为 0」运行。`MaxLing` 名是对的，所以只有当前值坏。
- 提示「操作结束后才弹」：`MagicStep` 里 return -1 收招，`MagicLeave` 才 `ShowMsgBox`，观感滞后。

### 修法
| 文件 | 改动 |
|---|---|
| `Scripts/WFG/core.lua` | 新增别名表 `PROP_ALIAS = { Ling = "LingV" }`，`WFG:Prop` 命中别名时二次读取；新增 `WFG:Ling(npc)` / `WFG:MaxLing(npc)` |
| `Scripts/Gong/YanTian/derive.lua` | 两处 `WFG:Prop(npc,"Ling")` → `WFG:Ling(npc)`；新增只读的 `D:Quote(M,npc,thing)`（物品名/等阶/品级/上限/是否已收录/消耗/当前灵气/是否足够） |
| `Scripts/Gong/YanTian/heal.lua`、`hall.lua` | 各自本地 `num()` 增加 `Ling → LingV` 回退 |
| `Scripts/WFG/ui/main_window.lua` | 灵气读取改 `WFG:Ling` / `WFG:MaxLing` |
| `Scripts/WFG/ui/derive_window.lua`（新） | 「衍天 · 解析」确认窗：560×380，正文列物品/等阶/品级/上限/是否已收录/消耗/当前灵气；灵气不足或不可解析时隐藏「开始解析」，只留「关闭」 |

## 2026-11-20 · 灵道剑按钮能看见但点不动：全局 cb0 不存在被 pcall 吞掉

### 现象
窗口能正常打开、数值正确，但所有按钮（存入/取回/±数量/确定/关闭）点击无任何反应，游戏日志也没有异常。

### 定位
日志 `LOG_11_20_12_43_5.txt` 第 444-448 行有 `[ui:lingdao] Show 开始/完成`，之后没有任何 `[灵道剑]` 开头的行 —— 说明点了按钮但处理函数一次都没执行，是事件没挂上去。

`Scripts/WFG/ui/lingdao_window.lua` 里 `addClick` 调用了 **全局 `cb0`**，而仓库里 `cb0` 只在 `create_confirm.lua:52`、`hall_window.lua:28`、`fgui_browser.lua:66`、`ningzhu_window.lua:51` 里以 `local function` 定义，**没有全局版本**。取 `cb0(fn)` 即抛 `attempt to call a nil value`，而 `addClick` 外层套了 `pcall`，错误被吞 → `o.onClick:Add` 从未执行。

### 改动
- 在 `lingdao_window.lua` 内补 `local function cb0(fn)`（`CS.FairyGUI.EventCallback0` 包装，与大厅窗口一致）。
- `addClick` 不再静默：失败时 `WFG:Error("ui.lingdao.click", err)` 并弹「按钮事件挂载失败：…」。

### 校验
`luac -p` 通过；deploy 49 文件；verify 49/49 SHA-256 全同；`acs_mod.py check` 0 错 0 警。

### 教训
窗口里凡是「看得见、点不动」且日志无异常，先查事件挂载函数的第一行依赖是否真的存在（全局 vs local），而不是怀疑 FairyGUI 命中测试。
